## 1. 譯文 PDF 閱覽卡頓

待查的可能原因（尚未量測）：

- BabelDOC 逐字放置中文字，每頁的繪圖指令比原文多很多，並嵌入中文子集字型
- 原文本身很重：簡報是經 iOS 重新匯出的 PDF（26 頁 17 MB），課本有大量向量圖（約 5 千個繪圖指令）
- 對照版用 `show_pdf_page` 把原文頁與譯文頁各包成一個表單物件，閱讀器每頁要畫兩份；字型、圖片沒有在兩份之間共用
- 對照版存檔時只用 `garbage=3`，沒有合併重複的字型與圖片

可以先量的：各輸出檔的大小與每頁繪製時間、與原文 PDF 比較；試 `garbage=4`、`clean=True` 重新存檔後是否改善。

### 1a. 使用者提供的分析（2026-10-27）

**主因**：BabelDOC 逐字排版，每個中文字都輸出成獨立的文字物件
`q BT /SourceHanSerifTW 10.9 Tf x y Td <一個字> Tj ET Q`，
物件數暴增約 10～20 倍。閱讀器對每個物件都要做狀態存取、字型切換、繪製，並建立一個文字片段（pdf.js 裡是一個 DOM 元素）。

**修正方式（無損）**：翻譯完成後、組對照版之前，重寫內容串流——
- 連續且圖形狀態相同的字合進同一個 `BT…ET`
- 同一條基線的字合成一個 `TJ`，用字型內的字寬算出精確字距
- 字型、字級、每個字的位置都不變

**原型實測**（12 頁與 144 頁 LaTeX 教科書，真實 BabelDOC 0.6.4 輸出流程）：

| 指標（每頁） | 現在 | 修正後 |
|---|---|---|
| 繪圖指令 | 7,464 | 345 |
| 文字片段（pdf.js） | 1,119 | 121（原文 158） |
| PDFium 頁面物件 | 1,059 | 89 |
| pdf.js 解析時間 | 35～70 ms | 8～22 ms |
| PDFium 繪製時間 | 24～28 ms | 11～14 ms |
| 檔案大小（144 頁） | 1.31 MB | 0.50 MB |

**驗證**：MuPDF 300 dpi 逐像素比對差異為 0，抽出文字完全相同；PDFium 只有反鋸齒的次像素差異，字位偏移小於 1/8 像素（576 dpi）。144 頁處理約 8 秒。

**限制**：原型環境連不到 Ollama 與版面模型，用假翻譯與簡化版面框代替（PDF 寫出段是 BabelDOC 原本的程式）；實際書的倍數可能不同，但成因相同。

**另一個可能成因**：BabelDOC 字型子集化有 60 秒時限，超時會把整套中文字型（每套 9～14 MB）直接嵌入。若譯文 PDF 比原文大好幾十 MB，代表這個問題也存在。（對照：本機簡報譯文 15.6 MB／原文 17 MB；課本譯文 7.7 MB／原文 7.8 MB——待確認是否有整套字型被嵌入。）

### 1b. 修正（2026-10-27）

`src/textbook_tw/compose/optimize.py`，翻譯完成後、組對照版之前執行（對照版跟著受益）：

1. **逐字合併**：只辨認 BabelDOC 寫的 `q <狀態> BT /字型 字級 Tf x y TD <字> Tj ET Q`；連續、圖形狀態相同的合成一個 `BT…ET`，同一基線用 `TJ` 加字距（字寬取自字型 `/W`、`/Widths`）。每行第一個字用原本的座標字串定位，位置完全不變。認不出來的內容原樣保留；頁面有 `Tz`（水平縮放）就整頁跳過。
2. **重複的圖形狀態**：BabelDOC 每個物件前都重設一長串 `/Gs1 gs/Gs2 gs/Gs1 gs…`（一頁兩千多個），連續的 `gs` 只留每個名稱最後一次，結果相同。
3. **只翻部分頁面時**：BabelDOC 的輸出仍透過結構標記與連結保留沒翻的原文頁（連同圖片），重新組一份只含現有頁面的 PDF。

**實測**（本機輸出檔）：

| 檔案 | 內容串流 | pdf.js 每頁指令數 | pdf.js 每頁解析 | 檔案大小 |
|---|---|---|---|---|
| 課本 120 頁 | 16.4 → 4.4 MB | 7,544 → 1,186 | 56 → 31 ms | 8.1 → 7.5 MB |
| 簡報 26 頁 | 0.42 → 0.11 MB | 1,512 → 146 | 14 → 10 ms | 16.2 → 16.2 MB |
| 論文第 1-2 頁（部分頁面） | — | — | — | 16.4 → 1.3 MB |

- 課本剩下的指令大多是原書的向量圖，不能再減。
- 檔案大小主要是圖片與字型，合併文字對大小影響不大。
- 字型都有子集化（最大 0.65 MB），沒有發生「整套字型被嵌入」的問題。

**驗證**：
- MuPDF 渲染逐頁比對：只做圖形狀態去重時差異為 0。
- 加上逐字合併後，抽出文字與每個字的位置都相同（位移小於 0.0005 pt）。少數字在 MuPDF 的字形快取取樣上落到相鄰的次像素，邊緣反鋸齒略有不同，肉眼看不出。
- 課本 120 頁處理約 4 秒。

已經翻好的檔案不用重翻：`uv run textbook-tw optimize output/`（處理資料夾裡所有 PDF，包含對照版）。

## 2. 跨領域文件的術語譯法

**使用者描述**：教科書和多數國外論文，內容不會只屬於一個領域。例如翻過的一篇複合材料多層板結構論文，同時有材料、力學、結構等用語；不能因為主題是材料，就全部套用材料名詞庫的譯法。希望翻譯更貼近人的判斷，依前後文的邏輯決定每個詞在這裡該怎麼翻。

**現況（記錄用，尚未動手）**：
- 一份 PDF 只有一張術語表，每個英文術語在全書只對應一個譯名
- 名詞庫之間譯名衝突時，依科目設定（profile）的優先順序挑一個；只有衝突很多的詞才標「待確認」讓使用者挑
- BabelDOC 用不分大小寫的字串比對，只要段落裡出現該英文詞，就把術語表譯名交給模型，不看這段在講什麼
- `glossary/sources.toml` 目前 19 個名詞庫沒有材料科學類，複合材料論文的材料用語只能從力學、機械、化工等名詞庫湊

### 2a. 做法（2026-10-27）

**A. 補候選、去雜訊**
- 加入國教院材料科學名詞：金屬材料、高分子材料、陶瓷材料、能源材料。
- 新增科目「材料與結構」（`materials`）；其他科目也加入統計學與材料名詞庫，排在後面。
- 同一個譯名出自幾個名詞庫就全部標出（標準差（航空太空、統計學）），模型與使用者都看得到它被多少領域採用。
- 大陸用語不列入候選：兩岸對照名詞的大陸譯名，以及含方差、置信、模量、信息等字的譯名。
- 冠詞開頭的詞組（a key→A 鍵）不收。

**B. 模型依上下文挑譯名**（`src/textbook_tw/glossary/resolve.py`）
- 對象：名詞庫譯名不一致的詞，以及每個字都很常見的詞組（first stage、key factor，可能只是一般說法）。
- 每個詞給模型：文件標題與開頭、這個詞在文中三處原文（分散在不同頁）、候選譯名與來源領域。
- 模型回答（Ollama JSON schema 限定格式）：
  - 選一個 →「模型建議」，note 寫理由
  - 都不合適，或只是一般英文 →「不套用」
  - 文中確實有不同意思 →「依段落」
- 每批 8 個詞；論文 101 個詞約 1.5～2.5 分鐘，課本約 500 個詞約 8 分鐘，一本書只做一次。
- App：術語確認畫面掃描完就自動開始，顯示進度、可停止；判斷完的結果和理由顯示在每個詞下面，可以改。
- 指令列：`glossary scan` 會接著判斷；`glossary resolve` 單獨判斷；翻譯時若還沒判斷過會先判斷。

**C. 依段落選譯名**
- 術語表 target 可以寫「剪力｜剪切」，翻譯時每段依意思挑一個。BabelDOC 的指令原本寫死「一律使用術語表譯名」，這類詞改寫成「從這幾個挑一個」。
- 翻完統計每個譯名用在幾段，顯示在完成畫面。

**實測**（複合材料論文，科目「材料與結構」，qwen3.5:4b）：
- 改對的：
  - standard deviation → 標準差
  - analysis of variance → 變異數分析
  - elastic modulus → 彈性模數
  - volume fraction → 體積分數
  - test sample → 試樣
  - delamination → 脫層
  - first stage → 初階
  - high resistance → 不套用（文中指抗裂性，不是電阻）
- 仍會選錯的：
  - filament winding → 燈絲繞線
  - aramid → 醯胺
  - set-up → 調整
  - confidence level 有時選「可信度」

  每次判斷的結果會因同一批的其他詞而略有不同。

- 依段落：shear 設為「剪力｜剪切」翻第 1–2 頁，5 段裡 3 段用剪切、2 段用剪力，沒有一段同時寫兩個。

**限制**：4B 模型的判斷不穩定，比較像「先幫你選好、附上理由」，最後仍要靠確認畫面檢查。換更大的模型（之後的模型評比）應該會明顯改善。
